\section{Introduction}
This is the project report added to our hand in for the Distributed Programming and Internet Architecture project in the spring semester of 2026. Here we will provide technical insight, an overview and background to our implementation of the peer-to-peer chat \textbf{Blabber}.
\subsection{Blabber Background}
As friends, we have regularly used Discord and other messaging applications to communicate.
\\
Throughout our studies, we became increasingly interested in privacy and computer security. We heard that Discord had introduced identity verification using government-issued IDs for some users. Shortly afterwards, a security incident involving one of Discord's third-party service providers exposed government ID photos of approximately 70,000 users \cite{discordbreach}. Seeing this made us question how much trust users should place in centralized platforms and motivated us to build our own chat application as part of this project.
\\
In the following chapters, we explain the design and implementation of Blabber and discuss the results, which were achieved during the project.
\section{Problem statement}
Because we planned our chat application with the idea of using it ourselves in mind, we had to find out what actually makes a chat comfortable and practical to use. In the following we will specify what requirements we thought of for our application. \\
Users should be able to:
\begin{enumerate} [a)]
    \item Create group chats for everyone to use with specific chat rooms.
    \item Keep track of messages and be assured that all participants have the same chat history.
    \item Send messages to users who are not connected through the rooms and receive missed messages when reconnected on the other end.
    \item Start a call with one or more users.
    \item Navigate the user interface while achieving their goals.

\end{enumerate}
 We not only wanted to be able to chat but also create a reasonably safe environment for our chatting history and communication. Therefore we formulated the following privacy and security requirements:
\begin{enumerate} [a)]
    \item Never store user information or related data, except on endpoints of communication.
    \item Prevent information disclosure through data in transit.
    \item Encrypt critical data stored on end devices. Critical data does not include chat history.
    \item Prevent endpoint impersonation through cryptographic peer identities.
\end{enumerate}

\section{Iroh as our background technology}
As we will elaborate on further, we used the Iroh networking stack and interfaces \cite{iroh} in our project.
Iroh provides the following building blocks we composed to achieve our final implementation.
\\ \\
\textbf{Iroh Endpoint} provides peer discovery and establishes QUIC connections between users identified by a public key, the \texttt{EndpointId}. This removes the need for a third-party communication handler.
\\ \\
\textbf{Iroh Docs} provides replicated, multi-writer
    key-value documents. That means every document is identified by a name
    and can be shared with others by a \texttt{DocTicket},
    which gives the receiver either read or write access to it.
\\ \\
\textbf{Iroh Gossip} propagates the updates of the documents between
    peers that are subscribed to the same document, without requiring
    everyone to be directly connected to each other.
\\ \\
\textbf{Iroh Blobs} stores the actual content that is referenced by
    document entries. A document entry only stores the hash of the entry, and
    the associated bytes are fetched separately by the blob store.
\\ \\

\section{Conflict-free replicated data structures}

Blabber uses the replicated document system provided by Iroh, which provides collaborative key-value documents with conflict-free replication. A CRDT allows multiple peers to modify the same data independently while ensuring that all replicas eventually converge without requiring a central server.
\\
In Blabber, spaces, members and chat messages are stored in replicated Iroh documents. Every peer keeps a local copy of the documents it has access to and can modify them locally. Whenever changes are made, Iroh synchronizes them with the other peers that have access to the same documents.
\\
Because Iroh already handles replication and conflict resolution, we did not have to implement our own synchronization or merge algorithms. This significantly simplified the implementation while still ensuring that all peers eventually reach the same state.

Blabber is implemented as a peer-to-peer desktop application. Instead of relying on a central server, every user runs their own instance of the application and communicates directly with other peers. The application consists of three main parts: the graphical user interface, the backend and the networking layer. Figure~\ref{fig:system_architecture} gives an overview of the interaction between these components.\\
The graphical user interface is implemented in Vue. It displays spaces, rooms, messages and voice calls and forwards user actions to the backend through Tauri commands.\\
The backend is implemented in Rust using the Tauri framework. It manages the local application state, encrypted identities and communication with the networking layer.\\
The networking layer is implemented using Iroh, which provides peer discovery, replicated documents and direct communication between peers. Blabber uses Iroh Docs to synchronize shared data, Iroh Gossip for document synchronization, Iroh Blobs for persistent storage and a custom protocol for voice communication.

\subsection{Core components}
The implementation is based on several core components.
\\
\\
\textbf{Identity:}
Each user owns an encrypted identity that is stored locally. The identity contains the user's display name, secret key and author identifier. After a successful login, the identity is decrypted and used to create the local networking node.
\\
\\
\textbf{Node:}
The node represents the local peer in the network. It creates and manages the Iroh endpoint, document engine, blob store, gossip service and router. It also keeps track of all spaces currently loaded by the user and acts as the connection between the frontend and the networking layer.
\\
\\
\textbf{Space:}
A space is comparable to a Discord server. It contains the shared information about a group, including its members and available rooms. This information is stored in replicated Iroh documents, allowing every participant to synchronize the same state.
\\
\\
\textbf{Room:}
Each space contains one or more rooms. Every room has its own replicated document in which chat messages are stored. Since each room has its own document, rooms can be synchronized independently.
\\
\\
\textbf{Invite:}
Users can join existing spaces through invite codes. An invite contains the information required to import the corresponding Iroh documents and connect to the space. Invites are stored locally so that spaces can be restored after restarting the application.
\\
\\
\textbf{Voice communication:}
Voice calls use a separate Iroh protocol. Audio is captured using CPAL, sent over Iroh datagrams and played back on the receiving peer. This allows voice communication without requiring a dedicated voice server.

\subsection{Backend architecture}

As mentioned, the backend is structured around a \textbf{Node} component. The node
coordinates the main application services and provides the connection between
the frontend and the decentralized networking layer. Requests from the Vue
frontend are received through Tauri commands and then forwarded to the
corresponding backend component.
\\
\\
During startup, the node creates an Iroh endpoint by using the secret stored in the user’s identity. Because the same secret is reused every time the user logs in, the endpoint identity remains the same across sessions. The node then initializes Iroh Gossip, the persistent blob store, the document engine and the protocol router. The router manages the protocols, which are used for document synchronization, blob transfer, gossip communication, voice communication and group call signaling.
\\
\\
The node also keeps track of all currently
loaded spaces. Each \textbf{Space} is represented by an information document
and a member document. The information document stores room records and the
member document stores the users that have joined the space. Both documents are
implemented using Iroh Docs and their serialized contents are stored using
Iroh Blobs.
\\
\\
Every room is represented by its own replicated Iroh document. When a room is
created, the backend creates a new document and generates a write ticket for it.
A room record is then
stored in the space's information document. It contains the room identifier,name and document ticket. Other peers can read this record,
import the room document and add the room to their local application state.
\\
\\
Messages are serialized using Postcard and written into the document belonging
to the selected room. The document entry contains a reference to the serialized
message data stored in Iroh Blobs. When a room is loaded, the backend queries
the existing entries, retrieves their contents from the blob store and creates
a local in-memory cache of the message history.
\\
\\
Rooms subscribe to live document events provided by Iroh Docs. When a local or
remote message entry is inserted, the backend retrieves and deserializes the
message, updates the room cache and creates an application event. These events
are sent through a Tokio broadcast channel and can be forwarded to the
frontend, allowing the visible chat to update without continuous polling.
\\
\\
Spaces are shared through serialized invites. An invite contains the identifier
and name of the space together with a read ticket for the information document
and a write ticket for the member document. After importing these documents, a
peer can discover the existing rooms from the information document and import
their individual message documents using the stored room tickets.

\subsection{Frontend architecture}
The frontend is implemented using Vue 3 and TypeScript. The frontend is responsible for displaying the user interface, handling user interactions and showing the current application state. Vue Router is responsible for switching between different views, while \texttt{App.vue} is the root component of the frontend.
\\
After logging in, users interact with the main application view. It provides access to spaces, rooms and chat messages. Functionality like creating spaces or managing identity settings is implemented through dialogs and a settings drawer. In preparation for voice calls, the settings drawer additionally lets users choose their preferred audio in-/output from the available devices on their system.
\\
The frontend communicates with the Rust backend through the Tauri framework. User actions, such as creating or joining spaces, creating rooms and sending messages, are executed by invoking Tauri commands.
\\
Shared application data, like spaces, rooms and messages, is managed using a Pinia store. Whenever the backend reports a change through a Tauri event, the corresponding data in the store is updated. The user interface then automatically displays these changes without requiring the user to refresh the application.

\subsection{Persistence and application restart}

To make spaces that a user has joined available again after the application is
closed and started again, Blabber persists the invite code used to join them.
When a space is created or joined, the invite is written to disk. \\
On startup we parse all the saved invites and then import the corresponding Iroh documents.
Then \texttt{Space::sync\_rooms} is called to restore every room that space
contains. This means Blabber itself stores no metadata like membership information or chat data outside of the replicated Iroh documents. The only persistent artifact is the invite code
required to derive access to the documents.

\section{Group voice calls}

Blabber supports voice communication between multiple participants through a mesh topology. Because we wanted to keep a fully peer-to-peer architecture, we did not include any forwarding of voice data or a relay unit. This means every participant needs to be connected to all others. The group call information that is needed for this connectivity is managed by a call room. It tracks known endpoint IDs and contains a call history through a replicated Iroh document. This is exactly the same pattern that is used for chat rooms. \\
Whenever a user joins the call room, the local node connects to all known users through a dedicated protocol, then sends a 16-byte call room identifier and waits for an acknowledgment before then registering the connection in a mesh voice channel. \\
Since all participants get one audio stream per participant, we need to mix them together on every client to receive a single audio stream containing all the participant's voices. We achieve this by having one jitter buffer per peer and mixing them together on a fixed time interval by averaging the buffered samples across all the participants that currently have data available. \\
With this design we avoid the need for a server but the number of needed connections scales quadratically with the amount of participants.\\

\section{Security considerations}
The most important goal of Blabber is privacy through decentralization. There is no central server that stores user accounts, chat history or other shared data. Every participant stores
only the information required for the spaces they have joined.

\subsection{Encrypted identities}

Each user identity is encrypted before being stored on disk. During identity
creation, the user's password is used to derive an encryption key using
Argon2 \cite{argon2}. This key encrypts the identity with ChaCha20-Poly1305\cite{chacha} before it is
written to persistent storage. Therefore, the identity can only be restored with the correct password.
Our current software holds the identities secret key in plaintext in memory. An attacker with memory access could use a memory dump to retrieve said secret. As a further improvement we could overwrite the secret with zeros on drop, lock the memory page and exclude it from core dumps.
\subsection{Authentication}
Peers are uniquely identified through their Iroh endpoint's public key.
This prevents endpoint impersonation but not display-name impersonation.
Because each identity contains a secret key that generates the same
Iroh endpoint whenever the user logs in, peers authenticate one
another through their cryptographic identities. With this architecture we don't need to rely on a central authentication server.\\

\subsection{Message synchronization}

Messages are stored inside replicated Iroh documents. Only users possessing the
required document tickets can import and synchronize the corresponding
documents. Because synchronization takes place directly between peers, no
intermediate server is needed to relay or permanently store chat data.
The access control to the synchronized documents happens on a per document scale. A member which holds the write key for a document can therefore write any key within it and not only their own entry. Our current implementation relies on legitimate peers that behave correctly. A malicious member could forge the self-reported author fields in messages since they are not bound to the entry's actual signer.
Any room participant could post messages impersonating someone else. We could fix this on our client but if a user has the write ticket they could still use their own software to write whatever they want into these documents. Since the username that is displayed currently does not have to be unique, impersonation could be achieved this way without needing to forge author IDs.

\subsection{Chat confidentiality}

We built our application first and foremost for our personal use. Since we wanted to migrate from company infrastructure to self-hosted software, our focus was primarily on functionality.\\
We have already started using Blabber in our friend group and we observed it to be working well.\\
One thing we encountered is that messages are only propagated through the state that a currently online client holds, the intended target will only receive the message when another client who holds it is online and sends it to them. In smaller groups the chance of other peers being online and propagating messages is smaller and could lead to longer time spans between sending and receiving. \\
We still have some known security gaps which make our application unfit for a broader distribution.
From this we can derive the following Blabber trust preconditions and consequences\\
Users know that establishing trust to other peers means knowing the risks of using our application and its architecture and accepting them. From this follows, that users should only share their identity and rooms with peers they trust.

\section{Conclusion}

With Blabber, we were able to build a working peer-to-peer chat application.
By using Iroh together with a Rust backend
and a Vue frontend, we implemented spaces, chat rooms, synchronized messages,
encrypted local identities and group voice calls.
\\
Most of the requirements we defined at the beginning of the project were
successfully implemented.
The application also keeps shared data on the participating endpoints and uses
encrypted connections for communication between peers.
\\
\\
During the project, we also identified several limitations. Users with write
access to a document can create arbitrary entries, and display names are not
directly bound to cryptographic identities. In addition, secret key material
remains in memory while the application is running, and the full-mesh topology
used for group calls does not scale well for a large number of participants.
\\
\\
Even with these limitations, we achieved our main goal of creating a
decentralized chat application that we can use within our own friend group. The
project also gave us practical experience with peer-to-peer networking,
replicated data, Rust, Tauri and Vue. In the future, Blabber could be improved
by adding stronger message authentication, application-level encryption, safer
handling of secrets in memory and a more scalable solution for group calls.
